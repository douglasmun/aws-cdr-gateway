# Common Pitfalls — Lessons Learned

> Extracted from CLAUDE.md. Authoritative pitfalls reference; CLAUDE.md points here.

Bugs that have been found and fixed. Each entry states the correct pattern so future code can be written right the first time.

A small number of entries (currently **#56**) record a **non-finding** instead: something audited, reported as a bug, and shown not to be one. They are here because an unrecorded non-finding gets rediscovered and re-reported — the cost is a wasted audit cycle and, worse, a "fix" to code that was already correct. Such entries say so in their first line.

### 1. Side-effect failures masquerading as CDR failures
Wrap every non-CDR side effect (`publish_result`, `delete_object`) in try/except with warn-and-continue. The upload to `SANITISED_BUCKET` is the only call that must succeed. Any unhandled exception causes EventBridge to retry — re-downloading and re-CDRing a file that was already sanitised.

### 2. Trusting `item.file_size` for decompression bomb defence
`item.file_size` is attacker-controlled in a crafted ZIP (central directory field). Read in 64 KB chunks and accumulate a running byte counter. Python 3.14's CRC check is a correctness guard, not a size limit — the chunked counter is independent and must stay even if `BadZipFile` would catch tampered ZIPs.

### 3. Silent `except: pass` hiding operational failures
`except Exception as exc: logger.warning(...)` — never bare `except: pass`. Silent failures mean CloudWatch alarms never fire and problems are invisible until a downstream audit.

### 4. Conflating CDR result topic with alarm topic
Two separate SNS topics. `CdrResultTopic` carries CDR result metadata for application consumers. `CdrAlarmTopic` carries CloudWatch alarm notifications for ops teams. Conflating them breaks application message parsing.

### 5. No DLQ = silent event loss after retry exhaustion
SQS DLQ + CloudWatch alarm on DLQ depth. Without a DLQ, events that exhaust EventBridge retries vanish permanently.

### 6. Oversized-file guard writing empty bytes to quarantine
`s3.copy_object(CopySource=..., Bucket=quarantine, Key=key)` then delete source. Never `put_object(Body=b'')` — that destroys the only copy of the file with no evidence.

### 7. `[Content_Types].xml` using container MIME types instead of OPC part types
Real Office files write OPC part-level types ending in `.main+xml` into `[Content_Types].xml` Override entries. Container-level types like `application/vnd.ms-excel.sheet.macroEnabled.12` are different strings. A remap table that only matches the container type silently leaves the part-level type in place. Test both forms — see `TestContentTypeRealOfficeTypes`.

### 8. Decompression bomb guard is mandatory on every ZIP read path
`_read_zip_entry_safe` must guard every ZIP-entry read. A 90 MB compressed upload that decompresses to multi-GB stays under the 100 MB pre-download guard and will OOM-crash an unguarded read path, creating an EventBridge retry loop. It must guard every ZIP read path — `cdr_office()` and `cdr_xlsb()`.

### 9. Not testing failure paths
Every try/except warn-and-continue helper needs a test that proves the success path completes even when that helper throws. If `_publish_result_safe` is not tested with SNS down, the fault isolation is untested and can be silently broken by a future refactor.

### 10. Trying to CDR xlsb binary sheets with regex or byte scanning
Scanning `xlsb` binary sheet data with a regex for known dangerous strings is not safe CDR — BIFF12 formulas can be obfuscated, split across records, or use future opcodes. The correct approach is `cdr_xlsb()`: use `pyxlsb` to extract only the plain cell values (cached formula results), then re-serialise with `openpyxl` as clean xlsx. No BIFF12 record bytes survive the conversion. Do not revert this to regex scanning or quarantine-always — the value-extraction approach is what makes xlsb files reachable by downstream consumers.

### 11. Content type test fixtures that don't reflect real Office output
Test `_sanitise_content_types` against the exact strings Microsoft Office writes — both the `*.main+xml` Override form and the `.12` Default form — for every macro-enabled format. A remap table that matches only one form silently leaves the other in place.

### 12. Writing security tests that manipulate file internals without understanding format validation
To test the chunked size counter: lower `_MAX_ENTRY_BYTES` to a sentinel value and read a legitimately-sized entry that exceeds it. Do not patch raw central directory bytes — Python's `zipfile` validates CRC at EOF, so patching the CD without fixing the CRC raises `BadZipFile` before the security check fires, making the test measure the wrong thing.

### 13. Asserting field code element removal when CDR neutralises in-place
`_strip_xml_macros` replaces the macro name with `_CDR_REMOVED_`, not deletes the element — preserving field begin/end marker balance. Assertions must check: `assert "MACROBUTTON HiddenButton" not in doc_xml` AND `assert "_CDR_REMOVED_" in doc_xml`.

### 14. ZIP anomaly handling is hard-reject, not log-and-proceed
All ZIP structural anomalies (bad magic, non-standard compression, duplicate entries, method mismatch) cause a hard reject — quarantine + delete source + return `"rejected"`. There is no CDR-proceeds path. An anomalous ZIP structure indicates attacker-controlled input that cannot be safely reconstructed.

### 15. `_publish_result_safe` truncation must handle both flat and nested report shapes
`_truncate_removed()` checks both `d["removed"]` (flat) and `d["report"]["removed"]` (nested). Call sites pass both shapes — guarding only the nested path leaves the flat path (e.g. oversized rejection) unprotected against a 256 KB SNS breach.

### 16. `onClick`/`onAction` regex must handle single-quoted attributes
In a Python regex character class, `[^\2]` matches the literal STX byte (octal 2), not a backreference. Use two explicit alternatives instead: `(?:"[^"]*"|'[^']*')`. Test with both quote styles.

### 17. EventBridge rule must exclude CopyObject to prevent processing loops
Without a `detail.reason` filter, the EventBridge rule fires on `CopyObject` events too. If the sanitised bucket ever accidentally shares an EventBridge rule with the source, CDR output triggers another CDR invocation. Restrict to `reason: [PutObject, CompleteMultipartUpload]`.

### 18. Infrastructure-dependent tasks cannot be completed without live credentials
`sam build`, `sam deploy`, `aws s3 cp`, and `docs/benchmark.py` all require live AWS credentials and the SAM CLI. Without them, commands fail silently and any reported results are fabricated. Produce complete, self-service artifacts (runbook + benchmark script) for human operators instead. Verify with `aws sts get-caller-identity` and `sam --version` before claiming any deployment action succeeded.

### 19. openpyxl serialises string cell values starting with `=` as live formulas
`ws_out.append()` / `ws_out.cell().value = v` both trigger openpyxl's formula-detection heuristic: any string beginning with `=` is written as `<f>...</f>` in the xlsx XML, making it a live formula when the file is opened. In `cdr_xlsb()`, a crafted xlsb can carry a `FORMULA_STRING` cached result like `=DDE("cmd","/c calc")` — pyxlsb returns this as `cell.v`. The fix: before writing, check `isinstance(v, str) and v.startswith("=")` and prefix with an apostrophe. Do not change the check order or skip it on any code path through `cdr_xlsb()`.

### 20. `cdr_xlsb()` bypasses `_read_zip_entry_safe` — must pre-read before handing to pyxlsb
pyxlsb reads ZIP entries internally, bypassing the chunked decompression counter in `_read_zip_entry_safe`. A 90 MB compressed xlsb passes the `_MAX_FILE_BYTES` pre-download guard but can contain a deflated sheet binary that expands to multiple GB. `cdr_xlsb()` must iterate all entries through `_read_zip_entry_safe` *before* calling `pyxlsb.open_workbook()`. Never remove or move this pre-read block.

### 21. Entity-encoded field codes must be neutralised WITHOUT decoding the whole XML part
Word's XML parser entity-decodes content before evaluating field codes, so `&#68;&#68;&#69;` is a live "DDE". The naive fix — `html.unescape()` on the whole part, then re-emit — **corrupts output**: a benign escape like `AT&amp;T` decodes to `AT&T`, producing invalid XML in the sanitised document. The correct approach (`_neutralise_encoded_field_codes`): match only runs of ASCII letters and numeric character references that contain at least one `&#...;` reference, `html.unescape()` **just that run** for the keyword check, and replace the whole run with `_CDR_REMOVED_` if it decodes to a dangerous keyword. Such a run only ever spans plain text, never markup, and a lone `&amp;` (decodes to `&`, not a letter) is never absorbed into a run — so legitimate escapes survive byte-for-byte. Do not reintroduce a whole-document `html.unescape()` that gets written back out. (`_neutralise_encoded_field_codes` in `lambda_function.py`.)

### 22. `WEBSERVICE` Word field code (no parens) is not caught by the `n3` pattern
`n3` requires `\s*\(` after the keyword — it matches the Excel function form `=WEBSERVICE("url")`. Word's field code form `{ WEBSERVICE "url" }` uses no parentheses. `WEBSERVICE` must appear in the `n_kw` pattern (keyword + argument, `\s+\S+` suffix) to catch the field code form. Same applies to `HYPERLINK` with UNC paths.

### 23. DDE pipe pattern must allow quoted/bracketed application names
The DDE pipe alternative `cmd|' /c calc'!A1` had an app-name class `[^\s\["']+` that *excluded* quotes and brackets — so `"cmd"|...`, `'cmd'|...`, and `[cmd]|...` (all valid Excel DDE forms) slipped through unmodified. The app-name portion must be `(?:"[^"]+"|'[^']+'|\[[^\]]+\]|[^\s\[\]"'|]+)` (`_strip_xml_macros` n3). Test all four quoting styles.

### 24. `CDR/Validation/ZipAnomalies` metric must be emitted on hard reject
`_validate_zip_structure` returns `(False, [anomaly])` on any structural anomaly and `(True, [])` when clean — it never returns `(True, non-empty)`. So the `if zip_anomalies:` branch after the validator is dead; the metric must be emitted inside the `if not valid:` hard-reject block. Without it the documented `ZipAnomalies` metric never fires and ops is blind to structural attacks. Test by patching `_emit_zip_anomaly_metric` and asserting it is called on bad-magic and duplicate-entry rejects.

### 25. PDF AcroForm root `/AA` and page `/FileAttachment` are separate vectors
The catalog `/AA` strip only covers `catalog["/AA"]` — the `/AcroForm` dict has its *own* `/AA` (fires JS on form calculate/focus) that must be deleted in the `/AcroForm` branch alongside `/XFA`/`/CO`. Separately, page-level `/FileAttachment` annotations embed a file via `/FS`(+`/EF`), bypassing the catalog `/Names./EmbeddedFiles` strip; the page annotation sweep must scrub `/FS` and `/EF` on any `/Subtype == /FileAttachment` annot.

### 26. `_download` must bound by S3 `ContentLength`, not just the EventBridge size field
The EventBridge `object.size` is checked pre-download, but the object can be swapped between the event and the read. `_download` must check `resp["ContentLength"]` against `_MAX_FILE_BYTES` before `Body.read()`, or a multi-GB swap OOM-crashes the container mid-read. A terminal `ValueError` here exhausts retries into the alarmed DLQ rather than crashing.

### 27. `s3:CopyObject` is not a real IAM action
There is no `s3:CopyObject` permission. A server-side copy is authorised by `s3:GetObject` on the source and `s3:PutObject` on the destination. The quarantine-copy statement in `template.yaml` must grant those two, not `s3:CopyObject` (which silently does nothing and fails posture scanners).

### 28. The dispatch must FAIL CLOSED — never pass an unrecognised extension through to SANITISED_BUCKET
A CDR gate's core promise is that everything in `SANITISED_BUCKET` was disarmed. The original dispatch `else` branch set `clean_bytes = file_bytes` and uploaded the raw file tagged `cdr-status: sanitised` — so any unknown extension (`.rtf`, `.svg`, `.html`, `.lnk`, `.iso`, …) was laundered into the trusted bucket. RTF/SVG/HTML are active-content carriers. The dispatch must check the extension is a known handled type and otherwise **quarantine + delete source + return `unsupported-format`** — content that was not disarmed must never be labelled sanitised. The passthrough metric is detective only; it is not a substitute for failing closed. Denylist routing here was the single highest-severity bug found in audit. Prefer allowlists everywhere a new format/part/action could appear.

### 29. Neutralisation regexes must not have catastrophic backtracking (ReDoS)
`_NUMERIC_ENTITY_RUN` and the DDE pipe pattern run via `.sub()`/`.subn()` over attacker-controlled XML text (`sharedStrings.xml`, worksheet XML, `document.xml`). A pattern of the shape `(?:A|B)* REQUIRED (?:A|B)*`, or unbounded `[^x]+` quantifiers that can backtrack with no anchoring suffix, is O(n²) — a single ~128 KB crafted text node then exceeds the 300 s timeout, EventBridge retries it, and the retry loop drains the 20-slot reserved-concurrency pool (remote upload-only DoS). Rules: use a SINGLE quantified alternation `(?:A|B)+` and apply extra conditions in the callback, not nested-quantifier regex; BOUND every `[^x]+` that isn't anchored (`{1,64}`, `{1,256}`); exclude `<`/`>` from arguments so a match can't span a tag boundary. Every neutralisation regex needs a timing regression test asserting a `'A'*200000` / `a*N|b*N` adversarial input completes in <1 s.

### 30. Any independently-imported module needs its OWN test file
This repo ships a single Lambda (`lambda_function.py`), covered by `test_cdr.py`. If a new independently-imported module is ever added, it must come with its own test file (setting env vars before import, mirroring `conftest.py`) — a module whose security guards rely on coverage of a sibling is verified by nothing.

### 31. Prefer allowlists; strip the PART, not just the relationship
A CDR tool's recurring failure mode is the denylist that "processes what it knows and passes the rest." Several real gaps shared this root: embedded OLE objects survived because only the `oleObject` **relationship** was stripped, not the `word/embeddings/*.bin` **part** (the payload bytes remain extractable from the output); `altChunk` imported HTML that the macro scrub never inspected; the PDF annotation **action allowlist** missed `/GoToE`/`/Rendition`/etc. Rules: when stripping a dangerous reference, also drop the part it points at (or rewrite it inert if the reference must remain to avoid a dangling id, as with hyperlinks); for PDF annotation actions, delete ALL `/A`/`/AA` rather than matching an action-type set; walk every action-bearing tree (pages, annotations, AcroForm fields + root, **outlines**). When a new format/part/action could appear, default to allow-known / reject-or-neutralise-unknown.

### 32. External hyperlink rels are neutralised in place, not deleted
Deleting a hyperlink relationship would leave the document's `r:id` reference dangling (corrupt file). Instead, in `_strip_rels`, any relationship with `TargetMode="External"` and the hyperlink type has its `Target` rewritten to `https://_CDR_REMOVED_/` — the rel element (and its `Id`) is preserved. This defeats UNC NTLM-theft (`\\host\share`) and phishing/SSRF URLs while keeping the file well-formed. `HYPERLINK_REL_TYPE` is deliberately NOT in `STRIP_REL_TYPES`.

### 33. The DDE pipe `!suffix` is anchored to a cell-reference shape, not any word
The DDE pipe form `app|topic!cellref` — a real DDE link target is always an Excel cell reference (`A1`, `$B$2`, `R1C1`). The `!`-suffix in the n3 / `DANGEROUS_FORMULA_PATTERN` is therefore `(?:\$?[A-Za-z]{1,3}\$?[0-9]{1,7}|R[0-9]{1,7}C[0-9]{1,7})`, NOT `[A-Za-z0-9$]+`. The broad form caused a false positive on benign prose like `Profit|Loss!Important`, corrupting it to an unbalanced `_CDR_REMOVED_(` in user-visible text. Keep the cell-ref anchor; test both a real DDE cell-ref link (neutralised) and benign `word|word!word` text (preserved).

### 34. An Office ZIP missing `[Content_Types].xml` is hard-rejected
Every OOXML package MUST contain `[Content_Types].xml` at the root. `_validate_zip_structure` rejects a ZIP that lacks it — otherwise an arbitrary archive renamed `.docx` would be CDR'd and labelled `sanitised` (the Lambda used to label any structurally-valid ZIP as a full CDR). Do not remove it; test fixtures for the Office path must include `[Content_Types].xml`.

### 35. S3 object-tag values must be sanitised to S3's charset — NOT percent-encoded
S3 tag keys/values allow only `[A-Za-z0-9 +\-._:/@]` and reject `%` (so percent-encoding fails with `InvalidTag`); `&`/`=` are the `Tagging` query-string separators (a value containing them fails with `InvalidArgument` and could inject extra tag pairs). `_enc_tag` therefore replaces any char outside `[A-Za-z0-9 +\-._:/@]` (minus `&`/`=`) with `_` and caps length (128 keys / 256 values) — it does NOT URL-encode. This matters most on the reject/error quarantine paths, where the tag value is an attacker-influenced reason string (e.g. `duplicate ZIP entry: 'word/document.xml'`, a CRC/limit error). A wrong implementation here silently sinks the quarantine write (caught only by a live deploy, never by mocked unit tests). Verify any change against real S3, not just pytest.

### 36. The CDR-error path quarantines but does NOT delete the source (intentional)
An unexpected exception in `cdr_office`/`cdr_pdf`/`cdr_image` → the handler copies the file to `error/` quarantine, publishes `error`, and **`raise`s** (no `_delete_source_safe`). The re-raise lets EventBridge retry (in case the error was transient) and ultimately routes to the DLQ; the source is preserved for investigation. This differs from a ZIP *hard-reject* (duplicate entry, bad magic/compression, missing Content-Types), which DOES delete the source because the input is definitively unprocessable. Do not "fix" the error path to delete the source — losing the original on a possibly-transient error is the regression.

### 37. PostScript/EPS parts inside an OOXML package must be stripped (part bytes AND declaration)
A valid OOXML package can legitimately declare a PostScript/EPS image part (`application/postscript`, `image/x-eps`, …) in `[Content_Types].xml` with the payload under `<app>/media/*.eps`. EPS is a Turing-complete interpreter language and a historic RCE surface (the GhostScript `-dSAFER` bypass family). The macro/OLE/ActiveX denylist never covered it, so both the declaration and the bytes passed through to `SANITISED_BUCKET`. Fix has **two independent strip mechanisms** because either alone is bypassable: (1) `_sanitise_content_types` drops any entry whose content type matches `_is_postscript_ct()` — which normalises case, surrounding whitespace, and RFC-2045 parameters (`;charset=…`) so a parameterised declaration can't evade — in both `Default` and `Override` forms; (2) the part bytes are dropped both by `.eps`/`.ps` suffix in `STRIP_ZIP_ENTRIES` **and** by a content-type-driven pre-pass (`_postscript_override_parts`) that runs before the main `cdr_office` loop and drops any part an `Override` declares PostScript *regardless of its filename* — e.g. an EPS payload stored as `word/media/image1.png`. The suffix rule alone misses the Override-on-arbitrary-name bypass; the content-type matcher alone leaves a dangling declaration. Both are needed. Tested by `TestPostScriptStrip` (Default/Override entry, clean-file no-op, suffix removal, Override-on-png bypass, no-extension bypass, evasive-`;charset` content type, and `_is_postscript_ct` normalisation). Inspired by DocBleach's PostScript content-type blacklist; hardened past it after an adversarial audit found the Override bypass.

### 38. RTF is rejected BY DESIGN — never give it a CDR handler
RTF's danger is **parser divergence**, not excisable content: embedded/linked OLE objects, remote-template references (`\object`/`\objupdate`/`\*\objclass`), and control words a forgiving consumer acts on — loose structure that Word interprets differently from any reconstruction parser you could write. A CDR pass can only defend the grammar IT parses; the attacker targets the grammar the *consumer* parses. History bears this out: CVE-2017-0199 (remote OLE template), CVE-2017-11882 / CVE-2018-0802 (Equation Editor), CVE-2023-21716 (font-table heap corruption). DocBleach's `\obj`→`\0bj` substitution is exactly the denylist trap to avoid — it *looks* like CDR but is a single-string bet against an inconsistent grammar. The correct posture is fail-closed quarantine. `FAIL_CLOSED_EXTS = {"rtf"}` is checked by a dedicated handler block that runs **before** ZIP validation and the unknown-extension gate, so the rejection is order-independent: even if a future edit wrongly adds `rtf` to `OFFICE_EXTS`, it lands in the fail-closed block and never reaches `cdr_office()`. Pinned by `TestRtfDeliberatelyFailClosed` (membership assertion + the belt-and-braces "added to OFFICE_EXTS" test). Do not add an RTF sanitiser; if RTF throughput is ever required, the answer is render-to-safe-format (e.g. RTF→PDF→CDR) out-of-band, not in-pipeline reconstruction.

### 39. Stripping a PART by name must also drop its RELATIONSHIP (else a dangling rel corrupts the doc)
`customXml/` part bytes are dropped via `STRIP_ZIP_ENTRIES`, but the relationship in `word/_rels/document.xml.rels` pointing at that part survived — a dangling rel that breaks strict OPC consumers (python-docx, Word: *"There is no item named 'customXml/item1.xml' in the archive"*), corrupting otherwise-legitimate documents (python-docx-authored .docx and many real Word docs ship customXml for doc properties / content-control databinding). Fix: the `customXml` (2006) and `customXmlProps` (2010) relationship types are in `STRIP_REL_TYPES`, so `_strip_rels` removes the rel alongside the part. General rule (mirrors pitfall #31): whenever you drop a part by filename, confirm any `.rels` entry pointing at it is also dropped — strip-part-and-rel, not just the part. Regression-tested (part AND rel both gone) and pinned by the `regression_customxml_rel.docx` corpus fixture.

### 40. Field-code neutralisation must be scoped to field carriers, NOT run over the raw XML part
The auto-exec (`AUTOOPEN`…) and keyword+argument (`LINK`/`INCLUDE`/`WEBSERVICE`/`HYPERLINK`…) passes originally ran a regex over the **raw XML** of each part. Keywords matched inside legitimate element/attribute *names* (e.g. `<w:link>`, `w:autoRedefine` in python-docx-authored `styles.xml`) and the `\S+` argument bound swallowed XML markup, emitting a value-less `_CDR_REMOVED_` attribute → invalid XML that strict consumers reject (*"Specification mandates value for attribute _CDR_REMOVED_"*) — corrupting legitimate, macro-free documents. Fix: run those two passes ONLY inside the parts where Word actually evaluates a field code — `<w:instrText>…</w:instrText>` element content and the `<w:fldSimple w:instr="…">` attribute — via `_scrub_field_code_carriers`/`_scrub_field_string`. Field carriers never contain element/attribute markup, so corruption is impossible; detection on real field codes is unchanged. The argument bound is also tightened `\S+`→`[^\s<>]+` (belt-and-suspenders: a match can never cross a tag boundary). **Behaviour change:** a field keyword sitting in plain `<w:t>` body text is no longer scrubbed — correct, since Word does not evaluate field codes there. The DDE-pipe / Excel-formula (`n3`), altChunk, action-attribute, and entity-encoded passes are unchanged (already XML-boundary-safe). Pinned by `regression_styles_field_keywords.docx` and the fldSimple-instr carrier test. Do NOT revert to scanning the whole part.

### 41. A second CDR front-end must reuse `cdr_dispatch`, never re-implement routing
The repo has two entry points — the AWS `handler` (S3/SNS-driven) and the local FastAPI `app.py` — but **one** decision core: the pure, I/O-free `cdr_dispatch(data, ext)`. It performs every routing and disarm step (size guard, legacy-OLE reject, RTF/fail-closed reject, ZIP structural validation, unknown-extension fail-close, then `cdr_office`/`cdr_pdf`/`cdr_image`) and returns a dict — `status`, `data`, `report`, the side-effect `metric` to emit, and whether to `delete_source` — but makes **no** S3/SNS/CloudWatch call itself. The wrappers map that result onto their transport (S3 buckets + SNS for the Lambda; HTTP status + headers for `app.py`). The trap a CDR gateway invites is a second front-end that copy-pastes "the routing it needs" and slowly diverges — so one path fails closed on `.svg` while the other launders it. Rule: any new front-end (CLI, queue consumer, another cloud) calls `cdr_dispatch` and only that; if you find yourself re-checking extensions or re-calling `cdr_office` outside `cdr_dispatch`, stop and route through it. `cdr_dispatch` itself is the single place a routing decision may change. Tested by `test_cdr_local.py::TestCdrDispatchRouting` (incl. `test_dispatch_does_no_io`) and the full 178-test Lambda suite, which exercises the same core through `handler`.

### 42. PDF decoder-RCE image filters (JBIG2/JPX) are neutralised in-place, not rejected
`/JBIG2Decode` and `/JPXDecode` (JPEG2000) are image compression filters with a history of *decoder*-level RCE — the exploit is a crafted stream that corrupts the viewer's parser, not "active content" the `/A`/`/AA`/JS sweep would catch (CVE-2009-0658; the FORCEDENTRY CVE-2021-30860 family). Didier Stevens' `pdfid` flags `/JBIG2Decode` for exactly this reason. CDR can't safely *transcode* the image (that would invoke the very decoder it distrusts), so `_neutralise_pdf_risky_image_filters` walks **every** stream object (page/form XObjects, `/SMask` soft masks, appearance streams — not just page resource dicts), and for any whose `/Filter` includes a member of `_RISKY_IMAGE_FILTERS` it rewrites the stream to a single inert byte, collapses it to 1×1 `/DeviceGray`, and deletes `/Filter`/`/DecodeParms`/`/SMask`/`/Decode`. **Decision: neutralise stream objects, do NOT reject** — JBIG2 is legitimately used by scanned documents, so rejecting the whole PDF would be a false-positive magnet. **Two non-obvious traps an adversarial audit caught (do not reintroduce):** (1) **inline images** — a risky filter can also ride an inline image (`BI … /F /JBIG2Decode … ID … EI`) inside a *content stream*, which lives in operator tokens (not a stream object), is invisible to the object walk, AND survives `pdf.save()`. `_reject_inline_risky_images` scans every content stream via `pikepdf.parse_content_stream` and **hard-rejects** the PDF (inline JBIG2/JPX is spec-violating + rare, so fail-closed is right). (2) **fail-open** — never swallow an exception once a stream is *identified as risky*; a `debug`-logged failure that leaves the risky filter in a "sanitised" file is the worst outcome. Once risky (or `/Filter` unparsable) → **re-raise** so the handler quarantines. Pinned by `test_jbig2_image_filter_neutralised`, `test_jpx_image_filter_neutralised`, `test_inline_image_jbig2_rejected`, `test_inline_image_benign_filter_not_rejected`, `test_malformed_filter_fails_closed`, + clean-PDF no-op. Add new decoder-RCE filters to `_RISKY_IMAGE_FILTERS`. (From the Didier Stevens gap analysis + its adversarial audit — `docs/cdr-gap-analysis-stevens.md`.)

### 43. Four bugs found by an adversarial code-quality audit (path evasion, annotation-AP bypass, cyclic /Kids, quarantine-failure source loss)
A dedicated multi-agent audit (find → adversarial verify → synthesise) turned up four hidden bugs, none caught by the existing 238-test suite:
- **STRIP_ZIP_ENTRIES prefix/suffix match used the raw ZIP entry name**, so `./word/vbaProject.bin`, `word//vbaProject.bin`, `/word/vbaProject.bin`, or `a/../word/vbaProject.bin` didn't literally start/end with a denylist pattern and passed through untouched — even though Word's OPC part-name resolution collapses all of these to the same canonical part at open time. Fix: `cdr_office` computes a separate `name_canonical = posixpath.normpath(name_lower).lstrip("/")` used **only** for the `STRIP_ZIP_ENTRIES` match (the original `name_lower` is untouched everywhere else — `[Content_Types].xml`/`.rels` detection, `ps_parts` membership, xlsb routing — to avoid changing behaviour on paths that were already correct). Pinned by `test_vba_macro_removed_path_evasion` (parametrised over the four evasive forms).
- **`_reject_inline_risky_images`'s docstring claimed annotation appearance streams were scanned, but the code never walked `/Annots`** — only page content streams and page-resource form XObjects. An inline JBIG2/JPX image hidden in an annotation's `/AP /N` (or `/D`, `/R`) content stream bypassed both the object-level sweep (inline images aren't stream objects) and the page-content walk. Fix: walk each page's `/Annots`, then each annotation's `/AP` entries; an AP entry is either a stream directly or a sub-dictionary of streams keyed by appearance state (checkbox `/On`/`/Off`) — **`pikepdf.Stream` itself also exposes `.items()`** (over its metadata dict, e.g. `/Filter`), so the code must check `isinstance(entry, pikepdf.Stream)` first, never just `hasattr(entry, "items")`, or it silently iterates the stream's metadata instead of its content and never detects the inline image. Pinned by `test_inline_image_jbig2_in_annotation_appearance_rejected`.
- **`_strip_acroform_fields`'s recursive `/Kids` walk had no depth or cycle guard**, unlike `_strip_pdf_outlines`'s `/Next`/`/First` walk (which has both). A malicious `field["/Kids"] = [field]` (or a two-field `A↔B` cycle) recurses forever — stack overflow / DoS. Fix: mirror the outline walk's guard exactly — a `_seen: set` of `.objgen` identities plus a `_depth > 1000` cutoff, threaded through the recursive calls. Pinned by `test_acroform_cyclic_kids_does_not_hang`.
- **The reject/unsupported handler path deleted the source object even when the quarantine upload had just failed** (the `except Exception as q_exc: logger.warning(...)` swallowed the failure and execution fell through to `if decision["delete_source"]: _delete_source_safe(...)` unconditionally) — destroying the only remaining copy of a file that needed investigation, violating the project's own "never destroy the only copy of unprocessable input" invariant (see pitfall summary in the checklist doc). Fix: track `quarantine_failed` and only delete the source `if decision["delete_source"] and not quarantine_failed`. Pinned by `TestQuarantineFailureDoesNotDeleteSource` (failure keeps source; success still deletes it, so the existing retry-loop-prevention behaviour is unchanged on the happy path).

**Deferred (considered, not implemented): unknown-part-family allowlist.** DocBleach additionally deletes any OOXML part whose top-level MIME family isn't `application|image|audio|video` (a coarse allowlist). A fine-grained content-type allowlist would harden the denylist posture further (per pitfall #28/#31), but the false-positive surface is wide — SmartArt, ink, embedded fonts, custom XML, theme variants, future Office part types — and a miss rejects/corrupts a legitimate business document (a production incident in a CDR gateway, not a security event). Validating it safely needs a corpus of real Office files, which this repo's synthetic in-memory fixtures don't provide. The dispatch already fails closed on unknown *extensions*; the residual risk is only unknown *parts inside an otherwise-valid OOXML package*, where every known-dangerous family is already on the denylist. Revisit only with a real-world Office corpus to guard against false positives.

### 44. Three availability/DoS bugs found by the same adversarial audit (ReDoS, silent depth-cutoff truncation, unenforced decompression-bomb cap)
- **`_scrub_field_code_carriers`'s `_INSTRTEXT_RE` was a single `(open)(.*?)(close)` regex with a lazy DOTALL body group.** When many `<w:instrText …>` opens have no matching close, the engine's lazy `.*?` scans forward to end-of-string for *every* unmatched open — O(n) work × n occurrences = O(n²). Benchmarked directly: 40,000 unmatched opens took 54 seconds, well within the existing 200 MB per-ZIP-entry decompression cap — a genuine Lambda-timeout DoS via a crafted `word/document.xml`. Fix: replaced the single regex-substitution pass with `_scrub_instrtext_elements`, a manual linear scan — `_INSTRTEXT_OPEN_RE.finditer` to find each opening tag, then a single forward `_INSTRTEXT_CLOSE_RE.search(text, open_m.end())` per open (never re-scanning already-consumed text) to find its close. If no close exists anywhere after an open, every later open is unclosed too (nothing after it can be a close), so the scan stops there — verified equivalent to the old regex's own non-nesting-aware "pair next open with next close" behaviour. Pinned by `test_many_unterminated_instrtext_does_not_hang` (40,000 unmatched opens must complete in under 2s).
- **`_strip_pdf_outlines`'s `/Next`/`/First` walk and `_strip_acroform_fields`'s `/Kids` walk were recursive with a `depth > 1000` cutoff that returns silently once hit.** A legitimately deep (non-cyclic) chain of ~1000+ nodes has the walk simply stop and return normally partway through — leaving deeper nodes' `/A`/`/AA`/`/JS` actions **unstripped while the function reports success**, so the file is uploaded to `SANITISED_BUCKET` labelled "sanitised" while still carrying live actions. Verified directly: a 1500-node `/Kids` chain left 504 fields' `/JS` untouched. Fix: converted both walks from recursive to iterative (explicit stack), removing the depth cutoff entirely — the identity (`.objgen`) seen-set alone fully prevents infinite loops on a cyclic chain, and a new `_MAX_WALK_NODES = 100_000` bounds total work against a pathologically large (but acyclic) tree without truncating any realistic document. Pinned by `test_pdf_deep_noncyclic_outline_chain_fully_swept` and `test_acroform_deep_noncyclic_kids_fully_swept` (5000-node chains, 100% swept).
- **`cdr_image` never explicitly set `Image.MAX_IMAGE_PIXELS`**, relying on Pillow's own undocumented default (89.5M soft-warn / 179M hard-error). Between those two thresholds Pillow only emits `DecompressionBombWarning`, which default warning filters do not raise — the image decodes (and gets re-encoded, doubling memory pressure) anyway, and at several bytes/pixel/buffer can approach this Lambda's 1024 MB memory ceiling well before Pillow's own error would fire. Fix: set `Image.MAX_IMAGE_PIXELS` explicitly at import time from `CDR_MAX_IMAGE_PIXELS` (default 40,000,000 ≈ 40 MP, sized to the 1024 MB budget), and inside `cdr_image` wrap the decode/re-encode in `warnings.catch_warnings()` + `simplefilter("error", Image.DecompressionBombWarning)` so anything over the cap raises and is handled by the existing `cdr_dispatch` exception path (quarantine, source not deleted) instead of silently proceeding. Pinned by `test_decompression_bomb_over_pixel_cap_rejected` / `test_image_under_pixel_cap_still_processed`.

### 45. Six correctness/data-loss/observability bugs found by the same adversarial audit (basename collision, SNS Subject charset, empty-dimension metric, missing legacy-OLE metric, substring over-match, header-injection anchor, animated-frame loss)
- **`_sanitised_key` replaced the extension outright when remapping** (e.g. `foo.docm` → `sanitised/foo.docx`), so a macro-bearing upload could silently collide with an unrelated, separately-uploaded, already-clean `foo.docx` on the exact same destination key — last-write-wins data loss with no warning. Fix: keep the original extension in the basename when it differs from the sanitised one (`foo.docm` → `sanitised/foo.docm.docx`). Pinned by `test_sanitised_key_no_basename_collision_across_extensions`.
- **`_publish_result_safe` built `Subject=f"CDR/{status}: {key}"[:100]` from an attacker-controlled S3 key with no charset sanitisation.** SNS `Subject` must be printable ASCII with no control characters; a key containing a newline or non-ASCII byte makes `sns.publish()` raise `InvalidParameterException` — and because the whole call is fault-isolated by design (must never block the delete/success path), that exception is silently swallowed, losing CDR result telemetry specifically for the most suspicious (adversarially-named) files. Fix: added `_sns_subject_safe()` (mirrors the existing `_TAG_SAFE`/`_enc_tag` S3-tag-sanitisation pattern) — strips anything outside printable ASCII `\x20-\x7e`, then caps at 100 chars. Pinned by `TestSnsSubjectSafe`.
- **`_emit_passthrough_metric` put the raw extension into a CloudWatch `Dimensions[].Value` unconditionally.** `Dimensions[].Value` has a botocore-enforced minimum length of 1 — a file with no extension at all (`ext == ""`) makes the *entire* `put_metric_data` call raise `ParamValidationError` client-side, dropping **both** datapoints in the request, including the mandatory dimensionless rollup that `CdrPassthroughAlarm` depends on (an alarm that then never receives data, per this same function's own docstring). Fix: substitute a non-empty placeholder (`"(none)"`) when `ext` is empty. Pinned by `TestPassthroughMetricEmptyExtension`.
- **The legacy-OLE (`LEGACY_EXTS`: `doc`/`xls`/`ppt`) reject branch in `cdr_dispatch` never set `metric="passthrough"`**, unlike the `FAIL_CLOSED_EXTS` branch immediately after it. Legacy uploads were correctly quarantined but invisible to `PassthroughFiles`/`CdrPassthroughAlarm` — an operationally-significant blind spot for a format class explicitly documented as intentionally rejected. Fix: set `metric="passthrough"` on that branch too. Pinned by `TestLegacyOleEmitsPassthroughMetric`.
- **`_neutralise_encoded_field_codes` used `kw in html.unescape(run).upper()`** — a plain substring containment check, not a word-boundary match — against `_ENCODED_FIELD_KEYWORDS`. Benign entity-encoded text that merely *contains* a keyword as a substring (`"PADDED"` contains `"DDE"`, `"UNLINKING"` contains `"LINK"`, `"RECALL"` contains `"CALL"`) was destroyed and replaced with `_CDR_REMOVED_`, corrupting legitimate document text that was never a field code. Fix: replaced the substring check with `_ENCODED_FIELD_KEYWORDS_RE` (`\b(?:KW1|KW2|…)\b`). Pinned by `TestEncodedFieldKeywordWordBoundary` (benign PADDED/UNLINKING preserved; malicious DDE/MACROBUTTON still neutralised).
- **`app.py`'s `_SAFE_EXT_RE = re.compile(r"^[a-z0-9]{1,16}$")` used `$`, not `\Z`.** In Python, `$` (without `re.MULTILINE`) also matches just before a single trailing `\n` — so an extension of `"docx\n"` passed the "safe" check and the embedded newline would ride along into a response header value (header-injection primitive). Fix: changed the anchor to `\Z`, which only matches true end-of-string. Pinned by `test_safe_ext_header_rejects_trailing_newline`.
- **`cdr_image` only re-encoded frame-by-frame for `save_fmt == "TIFF"` with `n_frames > 1`; animated GIF/WEBP fell into the single-frame `else` branch**, which calls `.convert()`/`.save()` on the base `Image` object — Pillow silently saves only the first frame. An animated GIF/WEBP upload was silently collapsed to a static single-frame image labelled with the original (animated) extension: real, user-visible data loss, not just an unstripped-metadata gap. Verified directly: a 5-frame GIF round-tripped through `cdr_image` came out with `n_frames == 1`. Fix: extended the multi-frame branch to `save_fmt in ("TIFF", "GIF", "WEBP")`, re-encoding every frame via `ImageSequence.Iterator` and preserving `duration`/`loop` for GIF/WEBP. Pinned by `test_animated_gif_all_frames_preserved` / `test_animated_webp_all_frames_preserved` / `test_single_frame_gif_still_processed`.

### 46. Eight availability/evasion bugs found by the high-utilisation production audit (aggregate zip bomb, XML encoding evasion, zip-slip, canonical duplicates, DTD, altChunk payload, .vml, animation budgets)
- **The decompression-bomb guard was per-entry only, with no aggregate cap.** `_read_zip_entry_safe` enforced `_MAX_ENTRY_BYTES` (200 MB) on each entry independently, so a package of many entries each *just under* the cap decompressed without limit. Measured directly: a 400 KB upload expanded to 419 MB, every entry legal; extrapolated, a 105 MB upload (under `CDR_MAX_FILE_BYTES`) yields ~107 GB and ~3 minutes of CPU against the 300 s Lambda timeout — after which EventBridge retries the same object, and with `ReservedConcurrentExecutions: 20` a handful of such uploads drains the entire concurrency pool. This is the availability failure mode that matters most at high utilisation: no crash, no alarm, just a wedged pipeline. Fix: added `_DecompressionBudget` (a single mutable counter, default `CDR_MAX_TOTAL_BYTES` = 512 MB — deliberately *under* the 1024 MB `MemorySize`, since a budget above the memory ceiling cannot bind before the OOM it exists to prevent) threaded through one package's whole extraction — `cdr_office`'s `[Content_Types].xml` pre-pass *and* its main loop, plus `cdr_xlsb`'s pre-read loop — consuming per *chunk*, not per entry, so the budget trips mid-entry rather than after. Also capped entry count at `CDR_MAX_ZIP_ENTRIES` (20,000) in `_validate_zip_structure`, and changed `_read_zip_entry_safe` to `bytearray.extend` instead of a chunk list + `b"".join()` (the latter doubles peak memory at exactly the moment a bomb is being read). Pinned by `TestAggregateDecompressionBudget` / `TestZipEntryCountCap`.
- **`_strip_xml_macros` decoded every XML part as `data.decode("utf-8", errors="replace")`.** OPC permits UTF-16 parts, and Word opens them. A UTF-16LE `word/document.xml` decoded through the UTF-8 path becomes `D\x00D\x00E\x00A\x00U\x00T\x00O\x00…`, which matches *no* scrub regex — verified: `removed: []`, output bytes byte-identical to input, `DDEAUTO` intact in the "sanitised" file. **Every** content-based disarm rule was silently bypassed by a one-line encoding change. The same `errors="replace"` also corrupted *clean* latin-1 parts, writing U+FFFD over accented text. Fix: `_decode_xml_part(data)` sniffs the BOM (`_XML_BOMS`, longest-first so UTF-32 is not mis-read as UTF-16) and returns `(text, encode_fn)`; the scrub re-encodes with the *same* codec, so the round-trip is lossless and BOM-preserving. Fall back is utf-8 then latin-1 — latin-1 is 1:1 over all 256 byte values, so it never lossily replaces. Never reintroduce `errors="replace"` on a part whose bytes are re-emitted. Pinned by `TestXmlPartEncoding`.
- **`_validate_zip_structure` accepted zip-slip entry names and wrote them verbatim to `SANITISED_BUCKET`.** `../../../../tmp/evil.xml`, absolute `/etc/x.xml`, backslash and drive-letter forms all validated clean and survived `cdr_office` into the output package. The Lambda itself never extracts to disk, so this is not a *local* traversal — it is worse: the gateway stamps the package "sanitised", and every downstream consumer that *does* extract inherits a traversal it has been told is safe. Fix: reject any entry whose `\\`-normalised name starts with `/`, contains a `..` path segment, or has a drive-letter second character. Pinned by `TestUnsafeZipEntryNames`.
- **The duplicate-entry check compared raw names, so path-equivalent duplicates passed.** `word/document.xml` plus `./word/document.xml` (or `word/sub/../document.xml`) validated as two distinct entries; Word resolves both to the same part and opens one, while CDR reports on the other — a classic parser-differential. Fix: the seen-set key is `posixpath.normpath(name.replace("\\","/").lower()).lstrip("/")`, the same canonicalisation pitfall #43 introduced for `STRIP_ZIP_ENTRIES`. Note the unsafe-name check runs *first*, so a traversal-form duplicate is rejected with the unsafe-name reason — the test accepts either hard-reject reason rather than pinning the message. Pinned by `TestDuplicateEntryCanonicalisation`.
- **No XML part rejected a `<!DOCTYPE>`.** OPC forbids DTDs outright, but `_sanitise_content_types`, `_strip_rels`, `_strip_xml_macros` and `_postscript_override_parts` all fed attacker bytes straight to `ET.fromstring`, which expands internal entities — ~1000x amplification from a few hundred bytes of nested `<!ENTITY>` definitions, inside a Lambda with a fixed memory ceiling. Fix: `_reject_xml_doctype(data, filename)` scans the first 4096 bytes (a DTD is only legal in the prolog) and raises at every one of those four call sites. Pinned by `TestXmlDoctypeRejected`.
- **`altChunk` payload parts survived even though the rel and the element were both handled.** Pitfall #31/#39 stripped the `aFChunk` relationship and neutralised `<w:altChunk>`, but nothing dropped the *payload* — `word/afchunk.htm` carrying `<script>` rode into the sanitised package. Dropping the reference is not dropping the content; a consumer that resolves the part by name rather than by rel still finds it. Fix: added `.htm`, `.html`, `.xhtml`, `.mht`, `.mhtml` to `STRIP_ZIP_ENTRIES`. This is the *converse* of pitfall #39 ("drop the part ⇒ drop the rel"): dropping a rel also obliges you to drop the part. Pinned by `TestAltChunkPayloadPartDropped`.
- **`cdr_office`'s scrub branch matched `.xml` only, so `.vml` parts were never scrubbed.** `word/drawings/vmlDrawing1.vml` is XML, is referenced by real documents, and carries `onClick`/`onAction` handlers and field-code carriers — verified surviving intact with an empty `removed` report. Fix: branch is now `name_lower.endswith(".xml") or name_lower.endswith(".vml")`. When adding a new XML-dialect part extension to the package, extend this branch, not just the content-type map. Pinned by `TestVmlPartScrubbed`.
- **`cdr_image` decoded every frame of an animation twice and enforced no aggregate budget.** It ran `ImageSequence.Iterator` once to collect frames and again to read durations — full re-decode of every frame purely for metadata — and `MAX_IMAGE_PIXELS` (pitfall #44) is a *per-frame* cap, so a 10,000-frame animation of small frames stayed under it while blowing the memory ceiling. Fix: single-pass collection accumulating `total_pixels` and `durations` together, bounded by `CDR_MAX_TOTAL_IMAGE_PIXELS` (80 MP) and `CDR_MAX_IMAGE_FRAMES` (2000). Note for fixtures: `Image.new("P", size, color=i)` frames collapse to `n_frames == 1` on save — build visually distinct RGB frames with explicit `duration`/`loop`, as the existing GIF/WEBP fixtures do. Pinned by `TestAnimatedImageResourceCaps`.
- **Supporting fixes from the same pass.** (a) `CdrReject` is a new exception class for a *deterministic verdict* — `cdr_dispatch` maps it to `rejected` (`delete_source=True`, `metric="zip-anomaly"`), never to the error/retry path, because retrying a structurally-invalid package produces the identical verdict forever. Reserve `ValueError` for "this input broke something"; use `CdrReject` for "this input is definitively not acceptable". (b) `cdr_dispatch` now raises if a CDR routine returns empty bytes — an empty object must never be uploaded labelled "sanitised". (c) All three boto3 clients are built with an explicit `botocore.config.Config` (`retries` standard/3, `connect_timeout=5`, `read_timeout=30`, `tcp_keepalive`); the default config's long socket timeouts hold a reserved-concurrency slot for minutes during an S3/SNS brownout. (d) `_download` used `resp["ContentType"]`, a `KeyError` on any object uploaded without one — now `resp.get(...) or "application/octet-stream"`. (e) `handler` parsed the extension from the whole key, so `archive.docx/notes` was treated as a `docx` — now taken from `posixpath.basename(key)`. (f) **A new cap is not shipped until both IaC paths set it.** These caps were added as SAM `Parameters` only; `terraform/` did not pass four of the seven `CDR_MAX_*` env vars, so a Terraform-deployed Lambda silently used the in-code defaults and could not be tuned at all (fixed #62). `tofu validate` cannot catch this — an absent env var is valid config — so CI now checks parity against the names `lambda_function.py` actually reads.

### 47. An extension allowlist gates ROUTING, not DECODING — pin the decoder too
`IMAGE_EXTS` decides which extensions reach `cdr_image`, but `Image.open(io.BytesIO(data))` picked its decoder by **sniffing content**, so `ext` only chose the *save* format. Every plugin in Pillow's registry (43 in the pinned build) was reachable by naming a hostile file `.png` — 37 of them outside the intended seven, including several with materially worse CVE histories than libpng/libjpeg: `FLI`, `PSD`, `DDS`, `SGI`, `XPM`, `JPEG2000`, `PCD`, `WMF`. Verified directly: PCX, TGA, SGI, DDS, PPM, IM and SPIDER payloads named `.png` were each decoded by their own plugin and accepted. Note `EPS` was on that list while `cdr_office` deliberately strips PostScript/EPS parts — the same content the Office path rejects reached a decoder through the image path. **This is not a disarm bypass** (output is still re-encoded); it is *native attack-surface amplification*: the attacker chooses which C decoder parses their bytes, which is the reachability precondition for a libtiff/FLI/DDS memory-corruption CVE. Since this is pure Python, the native libraries are the entire memory-corruption surface, and neither Pillow nor pikepdf pins its bundled native libs — a libtiff CVE arrives via a wheel rebuild, not a code change. Fix: `_PILLOW_FORMATS` passed as `Image.open(..., formats=_PILLOW_FORMATS)`. Deliberately the **7-format set, not the single declared extension** — extension/content mismatch among those seven is common in legitimate files, and rejecting real business documents is a production incident, not a security win (same false-positive reasoning as the deferred allowlist in #43). `UnidentifiedImageError` is translated to `CdrReject`, not left as a generic error, or EventBridge retries input that fails identically forever. The same asymmetry applied to PDF: the Office path validates magic + structure before zlib touches anything, while `cdr_pdf` handed raw bytes straight to QPDF's C++ parser behind only the size cap — now guarded by a `%PDF-` check within the first 1024 bytes (spec-permitted offset; the `pdf.save()` rebuild drops any leading polyglot prefix anyway). Pinned by `TestPillowDecoderAllowlist` and `TestPdfMagicGuard`. **General rule: an allowlist on the *name* constrains nothing about the *parser* — pin the parser explicitly.**

### 48. Pillow re-embeds `icc_profile` from `info` on PNG/TIFF — a silent metadata leak with a false audit record
`cdr_image` reported `"ICC profile"` in `removed` whenever the input carried one, but the PNG and TIFF encoders pull `icc_profile` out of the image's `info` dict — which **survives `.convert()` and `.copy()`** — and re-embed it unless explicitly overridden. Verified: a 588-byte sRGB profile came back intact in sanitised PNG, single-frame TIFF and 3-frame TIFF output while the report asserted removal. JPEG/WEBP/GIF happened to drop it, which is exactly why the bug hid. Two distinct failures: an attacker-supplied ICC blob is arbitrary-length attacker-controlled data and a historical colour-management-parser RCE surface (a clean covert channel at minimum), **and** the audit record claimed a removal the output contradicts — the worse half, since a "sanitised" label nobody can trust is worse than a known gap. Fix: pass `icc_profile=None` explicitly on **both** save paths (single-frame `save_kwargs` and multi-frame `save_all_kwargs`) rather than relying on per-encoder behaviour. **General rule: `report["removed"]` is an audit record, not a wish — if a test asserts a claim is in `removed`, another test must assert the output no longer contains it.** Pinned by `TestIccProfilePurged`.

### 49. Dispatching on a hardcoded OPC part name — resolve the RELATIONSHIP, as the parser does
The xlsb→`cdr_xlsb` conversion triggered only on `xl/worksheets/sheet*.bin`, but **OPC part names are arbitrary** — the workbook rel's `Target` is what a real parser follows. Verified: relocating the sheet binary to `xl/binparts/data1.bin` and repointing `xl/_rels/workbook.bin.rels` left pyxlsb still reading the cells while `cdr_office` took the plain ZIP path and emitted the BIFF12 sheet **byte-for-byte identical** — a full CDR bypass carrying FORMULA/DDE/`OLEOBJECT`/`DEFINEDNAME` records into the sanitised bucket. This is the same parse-not-scan lesson as #43's path-evasion bug, one layer up: there the *canonical form* of a name was the trap, here the *name itself* is not the authority. Fix: `_xlsb_worksheet_parts` pre-resolves every `_rels/*.rels` Target before the main loop (infolist() order is not guaranteed, and the rels part may follow the sheet), matching rel types on **local name** (`xlbinaryindex` is what xlsb actually uses; the same type ships under two namespaces — mirrors `_strip_rels`), resolving Targets relative to the rels file's owning directory, canonicalising via `posixpath.normpath`, and ignoring external (`://`) Targets. A budget trip while reading rels **fails closed** rather than falling through to the pass-through ZIP path. The documented invariant that a VBA-only/metadata-only xlsb stays on the ZIP path is preserved — the trigger was made *more precise*, not wider. Related: hostile BIFF12 makes pyxlsb/openpyxl raise bare `KeyError`/`ValueError`/`IndexError` (unresolvable rel target — pyxlsb reconstructs paths as `xl/{first}/{last}`, so not every relocation is even readable; a sheet name containing a character openpyxl forbids; an out-of-range column index). Those escaped as generic errors and burned the full EventBridge retry budget into the DLQ; `_convert_xlsb_sheets` is now split out so the whole traversal sits behind one `CdrReject` boundary. Pinned by `TestXlsbSheetResolvedViaRels`. **General rule: when a format resolves parts by reference, dispatch on the resolved reference — never on the conventional filename.**

### 50. Formula-injection neutralisation must cover the CSV prefixes, not just `=`
`cdr_xlsb` forced only cell values starting with `=` to text, on the reasoning that `=` is what openpyxl serialises as a live `<f>` element. That reasoning is correct **for the xlsx output** and was verified: `+1+1`, `-1+1` and `@SUM(A1)` all come back `data_type='s'` (inert text), only `=` becomes `data_type='f'`. But it scopes the threat to the wrong artefact. `+`, `-` and `@` are the standard CSV-injection prefixes, and Excel evaluates all four when a sanitised sheet is later exported to CSV and reopened — so a `@SUM`/`+DDE` payload survives CDR as harmless-looking text and goes live one export later, in a file the pipeline stamped "sanitised". Fix: `_FORMULA_INJECTION_PREFIXES = ("=", "+", "-", "@")`, checked after `lstrip("\t\r\n ")` because Excel tolerates leading whitespace ahead of the prefix. **No false-positive cost:** negative numbers arrive from pyxlsb as numeric cells (`data_type='n'`), never strings, so the widened `-` never sees them — verified, not assumed. Note the fixture limitation this exposed: `_make_xlsb` encodes FLOAT cells only, so string payloads cannot be driven end-to-end through `cdr_xlsb` and are tested at the guard boundary instead, with a control asserting an un-neutralised `=` genuinely produces `data_type='f'` (a test that only checks the guard's own predicate proves nothing without that control). Pinned by `TestFormulaInjectionPrefixes`. **General rule: neutralise for every consumer the sanitised artefact can reach, not just the format you are writing.**

### 51. A "no residuals" verdict is scoped to the taxonomy you audited against — re-audit, don't re-read
`docs/cdr-gap-analysis-stevens.md` concluded **"no open PDF residuals"** after a thorough pass against Didier Stevens' toolkit. That verdict was accurate *and* misleading: it was bounded by what `pdfid` enumerates, but read as absolute, and it is exactly what made the next three gaps invisible. Auditing the same PDF path against a *different* taxonomy (jonaslejon/malicious-pdf, tests 29–34) found three live vectors `pdfid` does not enumerate, each confirmed to survive `cdr_pdf` before the fix: (1) **catalog `/Threads`** — article beads hang off the catalog, not a page/annotation/action, so every action sweep misses them; dropped wholesale by `_strip_pdf_threads` (threads are navigation-only, no rendering role). (2) **`/FontMatrix` JS injection (CVE-2024-4367)** — PDF.js interpolated matrix elements into generated JavaScript, so a *string* element breaks out and executes; `_strip_pdf_fontmatrix` resets any non-numeric-or-wrong-length matrix to the spec default `[0.001 0 0 0.001 0 0]`. (3) **UNC in a stream `/F` external file spec** — the viewer fetches stream data from `\\host\share` on open and leaks NTLM, with **no action object anywhere in the file**, so the unconditional annotation `/A`/`/AA` sweep never sees it; `_strip_pdf_external_stream_refs` deletes `/F` plus the `/FFilter`/`/FDecodeParms` companions from every stream, and `/Alternates`/`/OPI` when their subtree actually names an external file (narrowed in #52).

**Three traps the adversarial audit of this very fix caught — all reintroducible:** (a) **Never gate a content sweep on an attacker-controlled discriminator.** The first `/FontMatrix` implementation only checked fonts with `/Subtype == /Type3`, because that is the CVE's context. But `/Subtype` is written by the attacker: relabelling the font `/Type1`, or omitting `/Subtype` entirely, walked the identical payload straight through — verified, four bypasses. The vulnerable sink parses the array wherever it finds it, so the sweep now checks **any dictionary carrying a `/FontMatrix`**. A well-formed matrix is untouched, so the wider scope costs nothing. (b) **`bool` is a subclass of `int` in Python** — `isinstance(x, int)` returns `True` for `True`, so a PDF boolean (which serialises as the bare token `true`, not a number) passed the "is it numeric?" check and survived in a sanitised file. Use an explicit `isinstance(x, bool)` rejection first; see `_is_pdf_number`. (c) **Scope the `try` to the smallest unit that must not fail-open.** Wrapping a whole per-key loop in one `try` means a single malformed key aborts the remaining keys *for that object*, leaving a live `/F` behind after a `debug`-logged non-event — the same fail-open shape as pitfall #42. Per-key `try`, not per-object.

**General rule: a gap analysis is a statement about the tool you compared against, never about the attack surface.** When a doc says "no residuals", read it as "clean against that one toolkit" and re-audit against a fresh taxonomy rather than treating it as coverage. Pinned by `TestMaliciousPdfTaxonomyGaps` (20 tests, incl. the four `/Subtype`-bypass variants, the boolean element, ObjStm-packed and indirect-array payloads, and three negative false-positive controls). Fixtures: `docs/fixtures/generate_fixtures.py` (`pdf_threads`, `pdf_fontmatrix_js`, `pdf_unc_xobject`, `pdf_lejon_multithreat`) — built from the spec with reserved-invalid hosts, no upstream code reused and no callback URLs.

### 52. `pdf.objects` enumerates only INDIRECT objects — walk the graph, and never key the seen-set on `id()`
The three sweeps added in #51 (`_strip_pdf_fontmatrix`, `_strip_pdf_external_stream_refs`) each iterated `pdf.objects`. That enumerates the **object table** — every *indirect* object — but a PDF dictionary may equally be written **inline**, directly under its parent. A Type3 font placed at `/Resources /Font /F1` as a direct dictionary, never `make_indirect`'d, is invisible to `pdf.objects`, so the entire CVE-2024-4367 `/FontMatrix` sweep was bypassed by an attacker simply *not using an object reference* — verified: the payload survived `cdr_pdf` with an empty `removed` list, i.e. the file was stamped sanitised while carrying the live vector. This is the same shape as #51(a): the first implementation trusted a structural choice the attacker controls. Fix: `_walk_pdf_nodes` traverses the reachable object *graph* from `/Root` (plus `pdf.objects` as a seed, so orphans still present in the file are not skipped either), bounded by `_PDF_WALK_MAX_NODES` against a depth-bomb.

**The subtle half — the seen-set key.** Cycle-breaking needs a stable identity per node. `objgen` supplies it for indirect objects, but every *direct* object reports the sentinel `(0, 0)`, so the obvious fallback is `id(node)`. **That is a latent skip bug:** pikepdf returns a **fresh Python wrapper on every access**, so a temporary wrapper can be garbage-collected and its address immediately reused by the next one — an unvisited node then collides with a `seen` entry and is silently dropped from the walk. It reproduced as a *timing-dependent* failure: the sweep worked when another sweep had run first (keeping wrappers alive) and failed on a cold `pikepdf.open`, which is precisely the shape that looks like flakiness and gets rerun rather than fixed. Key direct objects by their **path from the root** instead. Note that a payload-survival test cannot reliably pin this — the collision depends on allocator timing — so `test_walk_reaches_inline_nodes_on_cold_open` asserts the walk *reaches* an inline node on a cold open, which fails deterministically.

**Two supporting fixes from the same pass.** (a) Both sweeps **failed open** once a threat was positively identified: a broad `except Exception` around the mutation meant a failed `del obj[key]` or `/FontMatrix` reset was `debug`-logged and the file still shipped as sanitised. Both now raise `ValueError` at that point — matching the neighbouring `_neutralise_pdf_risky_image_filters` fail-closed convention. Reaching the handler means the key was *present* and the removal did *not* take; that is the one case that must never be swallowed. (b) `/Alternates` and `/OPI` were removed **wholesale**, but an `/Alternates` array whose images are all embedded streams is legitimate fidelity data with no external fetch — deleting it degrades the file for no security gain. Both keys are now scoped by `_subtree_has_external_ref` (fails *closed*: unreadable, over-budget or over-deep subtrees count as external). `/F` on a stream stays unconditional — it is always an external fetch. **The verdicts must be snapshotted before any mutation:** stripping `/F` from a nested alternate image would otherwise make its parent's subtree look clean by the time the sweep reaches it, making retention depend on traversal order.

**General rule: `pdf.objects` is the object *table*, not the object *tree* — any sweep that must see every node has to walk reachability. And never key a seen-set on `id()` of a wrapper object the binding recreates per access.**

### 53. Enumerating known containers is not a graph walk — and a blanket `except` around the loop swallows the sweep's own rejection
`_reject_inline_risky_images` is the fail-closed half of #42: a `/JBIG2Decode` or `/JPXDecode` *inline* image (`BI … ID … EI`) lives in operator tokens, not a stream object, so it cannot be neutralised in place and the PDF must be **rejected**. Its docstring said FAIL CLOSED. It did not. A deep probe found **six live bypasses**, every one confirmed to reach the sanitised bucket carrying the decoder-RCE payload.

Two independent causes, and the second is the one worth remembering:

**(a) Container enumeration.** The sweep visited page content streams, `/XObject` entries **one level** below the page and gated on `/Subtype == /Form`, and `/AP` appearance streams. That list is not the set of content streams a viewer executes. Missed: a form XObject **nested inside another** form XObject; a form XObject with **no `/Subtype`** (pitfall #51(a) again, one function over — the discriminator is attacker-written); **Type3 `/CharProcs`** glyph procedures, reached via `/Font`, not `/XObject`; **tiling `/Pattern`** streams; and **ExtGState `/SMask /G`** transparency-group streams. Fix: iterate `_walk_pdf_nodes(pdf)` and check *every* reachable stream. `parse_content_stream` simply fails on a non-content stream, so the wider scope costs nothing — there is no reason to enumerate.

**(b) The `except` swallowed the `raise`.** Widening the walk to every stream meant the sweep now parses embedded-file streams and font programs, whose operator tokens are arbitrary binary — `str(operator)` raised `UnicodeDecodeError` mid-sweep. The obvious fix, wrapping the operand loop in `try: … except Exception: continue`, also caught the sweep's **own** deliberate `ValueError` rejection. Proven with `sys.settrace`: execution reached the `raise` with `filters: ['/JBIG2Decode']` and then continued to the next operator. **A guard whose rejection path is inside its own `except Exception` is not a guard.** Fix: scope the `try` to *only* the operator/filter extraction, leaving the risky-filter `raise` outside it — pitfall #51(c) restated, and reintroduced one function away from where it was documented.

**General rule: when the failure mode of a sweep is "did not reach", enumeration is the bug — walk the graph. And when adding an `except` to a fail-closed function, check what else is raised inside its scope; a rejection is a `raise` too.** Pinned by `TestInlineRiskyImageContainers` (10 tests: all six bypasses, the page/`/AP` cases that already worked, a binary-stream tolerance test, and a false-positive control asserting an ordinary uncompressed inline image is still accepted). Both mutants — reverting to container enumeration, and re-widening the `try` — were confirmed to fail the new tests.

### 54. OPC binds a content type to a PartName, not a suffix — dispatch the XML scrub on the declaration
`cdr_office` rebuilds the package entry-by-entry and chose each entry's treatment by **filename suffix**: `[content_types].xml` → content-type sanitiser, `.rels` → relationship scrub, `.xml`/`.vml` → XML macro scrub. The last one is the authority mistake from #49, one layer over. An OOXML `Override` binds a content type to an **exact PartName irrespective of extension**, and a real consumer finds the main document part by following the package relationship, then parses it as XML because the *declaration* says so. Verified end-to-end: a document part stored as `word/document.bin`, declared `…wordprocessingml.document.main+xml` via an Override and pointed at by the `officeDocument` rel, skipped the macro scrub entirely — `cdr_office` returned `removed: []` while a live `DDEAUTO … cmd.exe` field code sat in the output. The confirmation that matters is the independent one: **python-docx opened the sanitised file and still saw the payload**, so this is not a theoretical parse difference. `word/document` with no suffix at all behaves identically.

Fix: `_xml_override_parts` resolves every Override whose content type is XML (`+xml`, plus the plain `text/xml` and `application/xml` spellings) in the *same* `[Content_Types].xml` pre-pass that already resolved PostScript parts, and the scrub dispatches on `suffix OR declared`. The suffix rule stays as the backstop for packages with no Override, and an unparseable/bomb-tripping Content-Types part yields an empty set rather than failing the file.

**Why `.rels` is NOT the same bug** — worth stating so the next audit does not "fix" it: OPC *requires* relationship parts at `_rels/<part>.rels`, so a consumer will not find them anywhere else. The part name is load-bearing there; it is only decorative for content parts. **False-positive cost is nil and was measured, not assumed:** a binary part mis-declared `application/xml` is left byte-for-byte intact (`_strip_xml_macros` leaves unparseable content alone), and all 24 on-disk Office fixtures + corpus samples round-trip unchanged.

**General rule: when a format has an explicit declaration mechanism, the declaration is the authority — a filename suffix is a convention the attacker is free to ignore.** Pinned by `TestXmlPartResolvedViaContentType` (6 tests: the `.bin`/no-suffix bypasses, a `.xml` control, the plain `application/xml` spelling, a binary-preservation false-positive guard, and a unit test that non-XML content types are not collected). Mutation-tested: reverting the dispatch to suffix-only fails 3 of them.

### 55. OPC declares content types TWO ways — resolving only `Override` leaves `Default Extension` wide open
The fix for #54 was right about the principle ("the declaration is the authority") and incomplete about the mechanism. OPC has **two** declaration elements in `[Content_Types].xml`, and both are equally authoritative: `Override` binds a content type to one exact PartName, and `Default` binds it to **every part carrying a given extension**. `_xml_override_parts` and `_postscript_override_parts` parsed only `Override`, so the entire `Default` half of the spec was unguarded — and `Default` is the *easier* of the two to abuse, because it needs no per-part bookkeeping at all.

Live bypass, found by probing the **OPC container layer as a taxonomy in its own right** (all four prior audits — Stevens, jonaslejon/malicious-pdf, ClamAV, DocBleach — target document *content*, so the package layer had never been swept deliberately). A package containing nothing but `<Default Extension="dat" ContentType="…wordprocessingml.document.main+xml"/>`, an `officeDocument` relationship pointing at `word/doc.dat`, and that part carrying a `DDEAUTO … cmd.exe` field code: **no Override anywhere**, so the XML macro scrub never ran and the payload shipped. Confirmed with the independent parser, as #54 requires — python-docx opened the *sanitised* output and still saw the live payload. Five variants all bypassed: `.dat` and `.bin` extensions, and rel Target spellings `/word/doc.dat`, `word/./doc.dat`, `word/sub/../doc.dat` (the Target spelling is irrelevant precisely *because* `Default` binds by extension, not by name).

Fix: one shared `_declared_parts(ct_xml, entry_names, matches_ct)` resolves **both** elements, with `_postscript_override_parts` and `_xml_override_parts` as thin wrappers over it — so the two halves can no longer drift. `Default` binds by extension, so it can only be resolved against the *actual ZIP entry names*, which the `cdr_office` pre-pass now passes in. Each resolved name is added in both its plain-lowered and `posixpath.normpath` forms, because one call site matches `name_lower` and the other `name_canonical`; a part named `./word/doc.dat` must be caught either way.

**Two probe lessons from this hunt, both already in the memory rules and both violated anyway.** (a) An early round reported "no bypass" on every case for the trivial reason that entries are **deflate-compressed** — `marker in raw` is False even when the payload is certainly present. A container probe must assert its precondition by *decompressing*, via the central directory **and** via a raw local-header scan (they can legitimately disagree). (b) A later round flagged `word/document.xml ` (trailing space) as a bypass, but so did `word/payload.txt` — the control. Both are merely *undeclared blobs*: unscrubbed, but unreachable by any consumer, hence not bypasses. **When the control also reports a bypass, the probe is wrong, not the code.** Pointing the `officeDocument` rel at the trailing-space part gets it scrubbed normally.

**False-positive cost measured, not assumed:** real packages use `<Default Extension="xml" …>` universally, so this widens the scrub set on essentially every genuine Office file — yet all 24 on-disk fixtures produce byte-identical output to unmodified `main`. (The single apparent hash delta was `xlsb_sheet_binary.xlsb`, whose openpyxl rebuild embeds a wall-clock timestamp; it varies run-to-run on unmodified code too. **Re-run a suspicious canary delta against stashed `main` before believing it.**)

**The sibling sweep, and why it found nothing.** The same container-layer question was then asked of the **PDF** path: incremental updates repointing `/Root`, stale payload catalogs, hybrid-reference `/XRefStm` files (where a classic-xref reader and an xref-stream reader resolve the same object number to different offsets), double `%PDF-` headers, ObjStm/xref-stream and linearised containers, encrypted files. **No bypass** — `cdr_pdf` ends in `pdf.save()`, which rebuilds from the reachable object graph and emits *one* revision (verified: single `startxref`, single `%%EOF`). Every attack in that class works by leaving two candidate documents in one file and steering which the reader picks; a rebuild that emits one document destroys the primitive by construction. **Ask what a subsystem's rebuild reconstructs — it predicts which bug classes can exist there at all.** `cdr_pdf` rebuilds the *document* and `cdr_image` rebuilds *pixels* (both immune); `cdr_office` rebuilds the ZIP *entry-by-entry, preserving part bytes* — deliberate, but it is precisely why declaration bugs are reachable in the Office path and nowhere else. Recorded in `docs/cdr-gap-analysis-stevens.md`; no tests were added, since pinning behaviour supplied by QPDF's rebuild would test the dependency rather than this codebase.

**General rule: when a format offers more than one way to declare the same thing, enumerate the mechanisms from the spec — closing one and calling the class fixed is how #54 became #55.** Pinned by `TestDefaultExtensionDeclaration` (9 tests: both extension variants, all three rel spellings, the independent-parser confirmation, the PostScript half, and two false-positive guards asserting `Default Extension="xml"` binds only real `.xml` parts and that `Default` resolves to nothing without entry names). Mutation-tested: dropping the `Default` branch fails all 9.

### 56. `a:fld` is NOT a field-code carrier — a payload the format never evaluates is not a finding
**No bug here; this entry exists to stop the next audit re-reporting a non-finding.** Chasing an apparent coverage asymmetry — the `.docx` corpus exercises both #54 and #55 declaration shapes, the `.pptx` corpus exercises neither — I built two PowerPoint packages with the main part named `.bin`/`.dat` and declared by `Override`/`Default Extension`, each carrying `<a:fld …><a:t>DDEAUTO … cmd.exe "/c calc.exe"</a:t></a:fld>`. Both came back with `removed: []` and the `DDEAUTO` string intact in the output. I reported it as a live bypass. **It is not one.**

`a:fld` is DrawingML, not WordprocessingML, and it holds **presentation-generated placeholder values only** — slide number, date, time — selected by a fixed `type` enumeration (`slidenum`, `datetime1`, …). It has no instruction-string grammar. The `<a:t>` child is a *cached rendering* of the generated value, not an instruction PowerPoint parses. Writing `DDEAUTO …` into it produces literal text on the slide. The payload was inert; it only looked dangerous to a grep, because I had chosen the string to match what a Word field code looks like.

The control settles it in one step, and it is the control #55 already tells you to run: a **conventionally-named `.xml` slide part with an ordinary `Override`** is equally untouched. That case has nothing to do with #54/#55, so the declaration mechanism was never the variable — the scrub simply does not treat `a:fld` as a carrier, by the deliberate scoping in #40 (`w:instrText` / `w:fldSimple` only, never raw XML, because raw-XML scanning corrupts legitimate markup). The comment on `_FIELD_KEYWORD_ARG_RE` says "the only places **Word** evaluates a field code," and that is precisely accurate.

The declaration machinery is in fact **format-agnostic and already covers pptx**: `_is_xml_ct` matches any `+xml` subtype and never mentions wordprocessingml, and `_declared_parts` matches on content type and never on a `word/` prefix. Demonstrated end-to-end rather than argued from the source — the *real* PowerPoint OLE/DDE vector (an `oleObject` rel plus `ppt/embeddings/oleObject1.bin` payload bytes) carried on a `.dat`-named slide part declared solely by `<Default Extension="dat">` is fully disarmed: `removed: ['rel:rId2 type=oleobject', 'ppt/embeddings/oleObject1.bin']`, with both indicators asserted present in the input first.

**General rule: a positive control proves the payload is *present*; it does not prove the payload is *executable*. Before reporting a survival as a bypass, establish that the format actually evaluates the construct you put it in — otherwise you have measured your own fixture.** This is #55's "when the control also reports a bypass, the probe is wrong, not the code" in a new costume: there the control was another undeclared blob, here it is a normally-declared part. Both times the tell was the same, and both times it was available *before* the finding was announced. No code change; no test added, since there is no behaviour here to pin.

### 57. A check whose result is discarded is an assumption wearing the costume of a test
Found by auditing this repo's own verification tooling — `docs/viewer-validation/build_realistic.py`, which builds the fixtures the manual viewer pass depends on. Two defects, neither in CDR:

1. **`check_loads()` computed a correct verdict and both call sites threw it away.** It returned `True`/`False` and was invoked as a bare statement, so the result was *printed* and never acted on. A package no engine could open still wrote the fixture, printed a success line and exited 0. That is precisely the `pptx_activex` defect the fixture exists to avoid — an unloadable package whose *input* proves nothing — reintroduced inside the tool built to prevent it. The file's own docstring claimed loadability "is asserted here", which is how it survived review: **I read the docstring, not the call site.**
2. **A hardcoded `"6 threat indicators"` while the probe checked 5.** The literal drifted from `threat_tokens()` and was then quoted in `CHECKLIST.md` and two PR bodies as though it were a measurement. Now derived with `sum(pre.values())`.

Fix: assert on the returned verdict, keeping `None` (engine not installed → *unverified*) distinct from `False` (engine rejected it → *failed*), so a missing toolchain does not silently become a pass. Mutation-tested, which is the only thing that proves a guard guards: rebuilding with an empty `_rels/.rels` now aborts on the input assertion, where before the identical mutant completed green.

**A false negative in a verification tool is worse than one in the code under test, because it does not fail — it congratulates you, and the false confidence then propagates.** Defect 2 shows the mechanism: a number that was never measured got restated downstream as if it had been. Both defects were in the *verification* layer while CDR itself was correct, which is the same shape as #56 and the #55 probe rounds. **The instrument keeps being the weak link, not the code.**

**General rule: a check that only prints is not a check. Any probe, canary or precondition must (a) have its result asserted at the call site, (b) distinguish "could not verify" from "verified clean", and (c) be mutation-tested against the exact defect it exists to catch — if you cannot make it fail on purpose, it is not protecting you.** Corollary for numbers: **derive counts from the probe, never type them** — a literal cannot drift silently, but it can and did drift loudly into three documents. See #55 (probe preconditions), #56 (control ordering); no test added here, since the generator is the test.

### 58. A MIME parameter defeats a `+xml` suffix test — and the OPC container-layer sweep that found nothing else
A 16-probe sweep of the OPC container layer — the same layer that produced #54 and the live #55 bypass — hunting a disagreement between how CDR resolves a part and how a real consumer does. **Four hypotheses, three positives, and all three died on their negative control.** The sweep is recorded because the *non-findings* are the result: this layer is now covered, and re-probing it needs a new hypothesis class, not a re-run.

- **H1 — ZIP entry-name spellings** (`word/./document.xml`, `word/sub/../document.xml`, `./word/…`, `word//document.xml`, case-flipped, backslash): all disarmed. The `posixpath.normpath` canonicalisation from #43/#46 holds.
- **H5 — rel `Target` forms** (absolute `/word/…`, `./`-prefixed, traversal, URL-encoded `%2e%2e` and `%2e`, backslash, case-flipped): all disarmed.
- **H3/H4 — declaration vs target disagreement**: an `Override` naming a *different* part than the rel target, and a part with no XML declaration at all, both leave the payload live in the output. **Refuted:** the content-type declaration is how OPC *locates* the main document part, so breaking it hides the part from every consumer as well as from CDR — LibreOffice headless and python-docx each refuse the package. Concealment and unreachability are the same fact here, which is precisely the structural difference from #55, where a valid `Default` declaration left the part genuinely resolvable and therefore genuinely dangerous.

**The one fix taken, as hardening rather than a bypass closure.** `_is_xml_ct` tested `ct.strip().lower().endswith("+xml")`. `.strip()` removes trailing whitespace — verified, a trailing-space content type was already disarmed — but a trailing **MIME parameter** moves the suffix off the end of the string, so `…wordprocessingml.document.main+xml; charset=utf-8` classified as non-XML and the part was never scrubbed. Against a part named `word/doc.dat`, where the content-type declaration is the *only* route to detection, a DDE payload reached the output with `cmd.exe` intact. It is **not** a live bypass: OPC declares a bare media type, so the parameterised form is malformed and both consumers refuse the package. Fixed anyway (`ct.split(";", 1)[0]`) because it costs nothing and removes a case that would otherwise be re-derived on every future audit. Pinned by `test_content_type_mime_parameter_still_classified_xml` (mutation-tested: all three parametrisations fail against the pre-fix classifier) plus `test_mime_parameter_does_not_widen_to_non_xml_types`, the false-positive guard asserting the media type is still required to be XML once the parameter is discarded.

**Two instrument defects from this sweep, both already-named failure modes walked into anyway.** (a) The first detector was `b"DDEAUTO" in output` — but the scrub replaces the macro *name* with `_CDR_REMOVED_` and deliberately leaves the keyword to keep the XML well-formed (#40), so a correctly-disarmed file reads as a bypass. Same marker-choice error the notes already record for `MACROBUTTON`. Assert on the **executable target** (`cmd.exe`) *and* on `report["removed"]` naming the scrub. (b) One intermediate run reported "SURVIVES" for every row **including the known-good canary** — which is the tell that the probe builder broke, not that the code regressed. **A baseline that disagrees with the canary invalidates the entire run**; read it as an instrument fault before reading it as a finding.

**General rule: a suffix test on a structured string must first discard the structure it does not model** — parameters, fragments, query strings. And when a probe turns up a positive, the negative control decides whether it is a finding: ask not "did the payload survive CDR?" but "does any real consumer accept the package that made it survive?" See #55 (the same question answered *yes*, hence a real bug), #56 and #57 (instrument-layer failures).

### 59. A resource cap that `return`s hands the attacker the sweep's coverage — bound the work, but fail closed
`_walk_pdf_nodes` bounded a hostile object graph with `_PDF_WALK_MAX_NODES` (500,000) and, on hitting it, **`return`ed**. That silently completed the generator, so every sweep built on it — `_strip_pdf_fontmatrix`, `_strip_pdf_external_stream_refs`, the inline-risky-image scan, the stream-filter sweep — finished with a *partial view of the graph*, `cdr_pdf` reported nothing unusual, and the file was uploaded to `SANITISED_BUCKET`. **Node count is attacker-controlled, so the cap was a switch the attacker could flip to choose how much of their own file got inspected.**

Verified end to end: a **10.6 MiB** file (against a 100 MB `_MAX_FILE_BYTES` — no size guard comes close) with 700,000 filler dictionaries and a CVE-2024-4367 `/FontMatrix` payload left a **live non-numeric `/FontMatrix` at `/Page[0]/Resources/AAA_early` in the sanitised output with an EMPTY `removed` list**. No exception, no failed assertion — the only trace was a `logger.warning` nothing acts on. Fix: `raise CdrReject`, matching the fail-closed convention of `_reject_inline_risky_images` (#53) and the #52 mutation handlers. **False-positive cost is nil and was measured, not assumed:** a 200-page document walks ~600 nodes and the malicious-corpus fixtures walk 10–107, so real files sit ~830x under the cap.

**The ordering detail that decides whether you find this at all.** The walk pops from a **stack** (DFS), so a payload inserted *before* the bulk filler is popped *after* it. The first probe put the payload last in insertion order, it popped first, and the file came back correctly stripped — a clean result that would have closed the hypothesis. Only inverting the insertion order put the payload in the truncated tail. **When probing a cap, the payload's position in the traversal is the variable under test — a single ordering proves nothing.**

**Two instrument defects from this probe, both re-finding lessons already in this file.** (a) The verification step iterated `q.objects` to look for a surviving `/FontMatrix` and reported "none" while the raw bytes plainly contained the payload — **exactly the `pdf.objects`-is-not-the-graph error #52 exists to document**, committed inside the tool built to check #52's fix. The payload was a *direct* object, so only structural resolution through `q.pages[0].Resources[...]` saw it. (b) The same run showed a byte-grep and a parser disagreeing; the grep was right and the parser probe was broken — the *opposite* of the usual direction (#H7 in this sweep needed semantic verification precisely because a deflated object stream defeats grep). **Neither byte-grep nor parser-probe is authoritative on its own; when they disagree, resolve the node by path before believing either.**

**General rule: every resource bound needs an explicit failure direction, chosen deliberately.** `return`, `break`, `continue` and a bare `except` around a bounded loop all *look* like bounding the work and all actually mean "ship whatever was inspected so far." If a cap can be reached by attacker-controlled input, reaching it is a verdict — `CdrReject` — not a truncation. Audit every `_MAX_`/budget constant for which of the two it does. Pinned by `test_walk_cap_rejects_rather_than_truncating` and `test_walk_cap_payload_in_truncated_tail_never_ships` (mutation-tested: both fail against the pre-fix `return`), plus `test_walk_cap_does_not_fire_on_ordinary_documents` as the false-positive guard. Related: #42 and #52a (fail-open `except`), #53 (a docstring claiming FAIL CLOSED while the code did not), #57 (a check whose result is discarded).

### 60. Auditing every cap's failure direction, and making "fail closed" a CI guard instead of a habit
The direct follow-up to #59: if one resource cap silently truncated, the others needed checking, and the checking itself needed to outlive the session that did it.

**Every remaining cap audited — no second instance.** Ten constants, each verified by *running* it (monkeypatched low, hostile input, observe the verdict) rather than by reading the code, since #53 is a docstring that claimed FAIL CLOSED while the code did not:

| Cap | On exceeding | Correct? |
|---|---|---|
| `_PDF_WALK_MAX_NODES` | `CdrReject` | fixed in #59 |
| `_MAX_WALK_NODES` (outlines, AcroForm) | `continue` / `break` → truncate | **NO — missed by this audit, fixed in #61** |
| `_EXTERNAL_REF_SCAN_MAX_NODES` | `return True` (= "is external", so the subtree is removed) | yes — closed by design |
| `_DecompressionBudget` / `_MAX_TOTAL_ENTRY_BYTES` | `CdrReject` | yes |
| `_MAX_ZIP_ENTRIES` | `_validate_zip_structure` hard-fail verdict | yes |
| `_MAX_ENTRY_BYTES`, `_MAX_FILE_BYTES` | reject | yes |
| `_MAX_IMAGE_FRAMES`, `_MAX_TOTAL_IMAGE_PIXELS` | `CdrReject` | yes |
| `_SNS_REMOVED_BYTE_BUDGET` | **truncates**, with an explicit `... and N more (truncated)` marker | yes — and it must |

That last row is why this guard is mutation-based rather than a grep for `return`/`break` inside a bounded loop. `_SNS_REMOVED_BYTE_BUDGET` caps a *report about an already-sanitised file*; rejecting there would discard a successful sanitisation over a long removed-list. **The failure direction is a judgement call about what the bound protects, so no syntactic rule decides it** — a linter would flag the one cap that is right to truncate.

**What is not a judgement call: whether a rejection that exists is load-bearing.** `scripts/check_fail_closed.py` mutates each `raise CdrReject` into a silent `pass` and re-runs the suite. A rejection whose removal the suite does not notice is decorative — nothing proves it fires, and a future refactor deletes it silently, which is exactly how #59 shipped. All 9 sites currently fail their mutant, so the existing coverage was sound; the guard exists so that stays true for rejections added later. Wired into `tests.yml` after the main test step (it costs one suite run per rejection).

**Two things the guard needed in order not to become the very defect it checks for.** (a) **A baseline green run before any mutant means anything** — without it a broken checkout reports every mutant "caught" and the guard passes vacuously (#57). This fired immediately and usefully: the first version exported `SANITISED_BUCKET`/`QUARANTINE_BUCKET`, which the test module defaults with `os.environ.setdefault` — that *yields* to the environment, so five tests asserting the literal `test-sanitised`/`test-quarantine` names failed. The documented "run pytest BARE" rule, rediscovered by writing a tool that broke it. (b) **A negative control on the guard itself**: a deliberately unpinned `raise CdrReject` was injected and the guard correctly named it by line. A checker never shown failing is an assumption (#57 again).

**General rule: when a review finds a bug class rather than a bug, the deliverable is the executable check, not the fixed instance.** This repo already had that instinct for docs (`check_test_count.py`, `check_cap_defaults.py`, `check_pitfalls_index.py`, `check_iac_parity.py`); security invariants deserve it more, because a doc drifting is embarrassing and a fail-open shipping is not. Related: #59 (the bug), #57 (instrument discipline), #53 (docstring vs behaviour).

### 61. The #60 audit enumerated caps it already knew about — `_MAX_WALK_NODES` was never on the list, and truncated in two sweeps
An external review (Codex, 2026-08-17) found the exact bug class #59 documents and #60 claimed to have swept clean, in a constant the #60 table never mentions.

`_strip_pdf_outlines` ended its walk with `continue` and `_strip_acroform_fields` with `break` on reaching `_MAX_WALK_NODES` (100,000). Both then returned normally and `cdr_pdf` shipped the file as sanitised. Reproduced end to end: a **12.2 MiB** PDF with a 100,002-node outline chain and a **10.6 MiB** PDF with a 100,002-node `/Kids` chain each came back "sanitised" carrying live actions — well under the 100 MB `_MAX_FILE_BYTES`, so no size guard is in the way. Fixed to `raise CdrReject`, matching `_walk_pdf_nodes`. Pinned by `test_outline_walk_cap_rejects_rather_than_truncating` / `test_acroform_walk_cap_rejects_rather_than_truncating` (exception) and the two `_payload_never_ships` tests (outcome), so any silent-completion replacement still fails.

**Why #60 missed it, and the lesson that is not "audit harder".** #60's table is a *hand-written enumeration* — ten constants someone remembered. `_MAX_WALK_NODES` is a *shared* cap used by two functions and named nothing like `_PDF_WALK_MAX_NODES`, so it fell out of recall. `check_fail_closed.py` could not catch it either: that guard mutates rejections that **exist** and asks whether a test notices; it is structurally blind to a cap that never raises in the first place. **A guard that verifies existing invariants cannot find a missing one.** The complement to `check_fail_closed.py` is enumeration from the source, not from memory: `grep -n '_MAX_[A-Z_]*\|_BUDGET' src/lambda_function.py` yields the real list, and every hit must be traced to an explicit failure direction before the audit counts as complete.

**General rule: when a review concludes "no second instance", state how the instances were enumerated.** "I checked the caps" and "I listed every `_MAX_`/budget constant in the module and traced each" are different claims with the same wording, and only the second one is falsifiable. Related: #59 (the bug class), #60 (the audit that missed this), #57 (a check that cannot fail is not a check).

### 62. A runbook command that hardcodes a prefixed resource name points the operator at somebody else's production
The two Low findings from the same external review as #61, plus the guard that makes the class non-recurring.

`docs/deployment-runbook.md` told operators to inspect `--rule cdr-s3-object-created`, but Terraform names it `${var.resource_prefix}-s3-object-created` (`terraform/main.tf:363`). The same runbook, two sections earlier, tells the reader **not** to deploy at the `cdr` default — a live askkaifbot service already owns those names in ap-southeast-1 (see the deploy notes). So the documented command is wrong for exactly the readers who followed the documented advice.

**Verified against live AWS (2026-08-17), and the real behaviour is worse than "the command fails".** The original write-up guessed "best case `ResourceNotFoundException`, worst case they inspect the unrelated service". There is no best case. `aws events describe-rule --name cdr-s3-object-created` in ap-southeast-1 returns **`ENABLED`**, and `list-targets-by-rule` shows it wired to `arn:…:function:cdr-lambda` — the live askkaifbot service. An operator deployed at `cdr-staging`, following the old runbook, gets a green light from *somebody else's production* and concludes their own pipeline is correctly wired. A command that errors is self-correcting; one that confidently answers about the wrong resource is not. **When estimating a doc bug's blast radius, run the wrong command — do not reason about what it would probably do.** Also fixed alongside: `MaxMemoryUsed` is **not** an `AWS/Lambda` CloudWatch metric — the query returns an empty `Datapoints` list, which reads as "no memory pressure" but means "no such metric"; `docs/benchmark.py` had it right all along, parsing the REPORT log line via Logs Insights. Also confirmed live, with the control in both directions: `list-metrics --metric-name MaxMemoryUsed` returns **0**, the old command returns `null` with exit status 0, and the identical command shape against `Duration` returns **2** metrics — so the query form was never the problem, only the metric name. The replacement Logs Insights query returns `max_mem = 130` MB against the real log group.

**Why a guard, and why this one is narrow.** Both bugs are IaC/doc drift, the class `check_iac_parity.py` and `check_cap_defaults.py` already exist for — but neither looks at *command literals*. `scripts/check_runbook_prefix.py` closes that: it derives the prefixed-name suffixes **from `src/template.yaml` and `terraform/main.tf` at runtime** (13 of them) rather than hand-listing, which is #61's lesson applied one commit later, and flags a `cdr-<suffix>` only where it is *passed to a command* — an option-value run or a `/aws/lambda/…` path. Prose, parameter tables and S3 tag names (`cdr-status=sanitised`) are deliberately untouched: the runbook must be able to say "do not leave `ResourcePrefix` at the `cdr` default", and a guard that flags its own advice gets silenced rather than fixed.

**The exemption is the interesting part.** Section 8's `ResourceExistenceCheck` block investigates the *foreign* `cdr-lambda` the reader did not deploy — there the literal is correct and `$PREFIX-lambda` would be actively wrong. No syntactic rule separates that from a genuine bug, so the doc declares it inline with a reasoned `<!-- prefix-literal-ok: … -->` marker, and the guard prints every exemption in its summary so a growing pile is visible rather than quietly normal. **A marker with no reason is itself a failure**, as is one placed *inside* a fenced block — an HTML comment there is not a comment, it renders literally and lands mid-command when the command is line-continued (found by writing it that way first).

**Two guard bugs caught by its own negative controls, which is the point of running them.** (a) The first regex matched only a name sitting immediately after `--opt`, so an injected `--dimensions Name=FunctionName,Value=cdr-lambda` — the form the runbook's own CloudWatch commands use — passed clean. Matching the whole argument run fixed it. (b) The pass/fail harness initially counted `grep -c 'hardcodes'`, which also matched the help text, so a failing control *looked* like it fired. Five controls now run: the pre-fix runbook, an empty exemption reason, a marker inside a fence, a newly-injected literal, and the current file as the false-positive canary. **A guard never shown failing is an assumption (#57); a guard shown failing by a broken harness is worse, because it looks like evidence.** Related: #61 (enumerate from source), #57 (instrument discipline), #60 (making a rule a CI guard rather than a habit).
